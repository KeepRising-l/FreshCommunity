# FreshCommunity 技术选型介绍

> **课题名称**：社区生鲜团购平台的设计与实现
> **项目名称**：FreshCommunity
> **整理日期**：2026 年 10 月 14 日
> **版本依据**：后端 `backend/pom.xml`、前端 `frontend/package.json` 和现有源码。文中的版本表示本项目采用或声明的版本，不代表最新版本。

## 一、选型目标

技术选型围绕本课题的业务和实现规模确定，重点考虑以下要求：

1. 能清楚实现注册登录、角色权限、商品维护和团购交易等 Web 功能。
2. 能在数据库事务中管理订单、库存、团购人数和退款状态。
3. 可以编写条件更新等明确 SQL，处理并发扣库存和防止重复状态变更。
4. 支持浏览器端的多角色页面，便于本地开发和毕业设计演示。
5. 部署依赖和运行环境保持在单体项目可管理的范围内。

## 三、后端与数据访问选型

### 3.1 Java 17 与 Spring Boot

后端使用 Java 17 和 Spring Boot 3.2.5，按 Controller、Service、Mapper 分层：Controller 负责接收请求和参数校验，Service 负责业务规则与事务边界，Mapper 负责数据库读写。该结构对应项目中的认证、商品、团购、订单、评价、消息和订阅等模块，便于把接口处理、业务判断和 SQL 操作分开维护。

Spring Boot 同时承载内置 Web 服务、事务配置和 `@Scheduled` 定时任务。当前项目以单体应用运行，不需要额外搭建服务注册、远程调用或分布式配置设施。

### 3.2 MyBatis-Plus 与 MySQL

项目使用 MyBatis-Plus 执行常规增删改查，并通过 Mapper 自定义 SQL 实现库存扣减和状态条件更新。选择这组方案的主要原因是，团购交易需要明确控制更新条件及受影响行数。例如，扣减库存时直接要求库存不小于购买数量；更新影响一行表示成功，影响零行则说明库存不足或状态已变化。

MySQL 保存订单、库存和团购数据。库存变更、订单状态变化及相关通知可在同一数据库事务中完成，符合当前单体和本地演示规模。团购商品价格在开团时写入 `group_buy_item.price_snapshot`，之后维护商品目录价格不会改写已创建团购的价格快照。

项目没有使用 Redis 作为库存账本，也没有引入消息队列。对当前规模而言，把关键交易状态保存在同一关系数据库中更直接，部署和一致性处理也更简单。若后续扩展为多实例或更大吞吐量，再评估缓存、消息队列和定时任务协调机制。

### 3.3 Spring Security 与 JWT

Spring Security 负责认证过滤和角色授权，JJWT 负责 JWT 的创建与解析。系统登录后签发令牌，前后端分离的页面请求通过 Bearer Token 携带身份信息；后端按角色和资源归属校验权限，例如团长只能操作本人团购，普通用户只能访问本人订单和消息。密码使用 BCrypt 哈希保存。

JWT 适合当前浏览器客户端与无状态接口的实现方式，减少服务端会话管理。当前项目没有令牌黑名单或刷新令牌机制，因此已签发令牌在有效期内不能主动撤销；这是现有实现的安全边界。

## 四、前端选型

### 4.1 Vue 3 与 Vite

前端使用 Vue 3 单页应用，按页面和公共组件组织三类角色的功能。Vue Router 负责页面路由和登录状态拦截，Pinia 保存用户令牌、当前用户和通知未读状态。Vite 提供本地开发和构建能力，开发配置将 `/api` 请求代理到后端。

本项目页面以表单、列表、状态展示和交易操作为主，Vue 的组件结构便于复用团购卡片、订单卡片、状态徽章等界面元素。该选择也与当前代码组织和开发方式保持一致。

### 4.2 Element Plus 与 Axios

Element Plus 提供表单、对话框、表格和提示等通用组件，项目在其基础上应用自己的颜色变量和公共样式。Axios 通过统一请求封装携带 JWT，并集中处理认证失效等响应。这样可以减少各页面重复编写的请求与状态处理逻辑。

当前前端包含用户主流程以及团长、管理员的基础页面；界面精修和移动端响应式适配的完成度需查看 [`实现清单`](implementation-inventory.md) 与界面设计资料，不能仅根据技术栈推断为全部完成。

## 五、架构和关键机制的技术配合

系统采用前后端分离的分层单体架构：

```text
浏览器中的 Vue 页面
        │ HTTP /api，Bearer JWT
        ▼
Spring Boot Controller
        ▼
Service（业务规则、事务）
        ▼
MyBatis-Plus Mapper 与自定义 SQL
        ▼
MySQL
```

| 业务问题 | 对应技术措施 |
| --- | --- |
| 并发下单超卖 | MySQL 条件更新执行原子库存扣减，检查受影响行数 |
| 并发重复成团或重复退款 | 使用带预期状态的条件更新和业务状态检查 |
| 订单、库存及人数变化不一致 | Service 事务统一处理关联数据变更 |
| 未支付订单超时、团购到期 | Spring `@Scheduled` 按约定周期扫描并处理 |
| 角色越权和跨用户访问 | Spring Security 角色授权加业务数据归属校验 |
| 支付渠道尚未接入 | `PayService` 与模拟支付实现隔离 |

## 六、方案取舍

| 需要决定的问题 | 当前选择 | 取舍理由 |
| --- | --- | --- |
| 整体架构 | 前后端分离、后端分层单体 | 页面与接口职责清楚，同时保留单一后端服务，适合本地开发和毕业设计演示 |
| 数据访问方式 | MyBatis-Plus 与自定义 SQL | 常规 CRUD 开发较简洁；库存扣减和状态条件更新可直接检查 SQL 与影响行数 |
| 交易数据存储 | MySQL | 订单、库存、团购状态集中存放，便于在同一数据库事务内处理 |
| 库存并发控制 | 数据库原子条件更新 | 逻辑清楚且无需额外库存服务；当前演示规模不需要引入 Redis 预扣链路 |
| 前端组件 | Vue 3 与 Element Plus | 便于按页面和公共组件实现多角色表单、列表和状态操作 |
| 定时任务 | Spring `@Scheduled` | 到期团购和超时关单属于当前单体应用中的周期扫描任务，不需要独立任务平台 |
| 消息方式 | 数据库站内消息 | 业务事件与消息记录可由后端统一管理；短信、App 推送等外部触达不在本期范围 |

采用单体方案并不代表系统已针对多节点部署做好调度协调。将来若运行多个后端实例，需要进一步设计定时任务的互斥或幂等保障，并重新检查并发与消息处理。

## 七、AI 导购选型与实现边界

AI 导购使用 `DemandParseService` 抽象需求解析，由 `LlmParseService`（LLM 优先）与 `RuleDemandParseService`（规则兜底）两个实现组合：配置 OpenAI 兼容密钥时调用大模型并把口语词归一映射到在售商品名，无密钥、超时或响应不合法时自动回落规则解析。调用封装于 `AiClient`，接口协议为 OpenAI 兼容（`base-url / api-key / model / timeout-seconds` 均可配置），可指向 DeepSeek、通义等任意兼容供应商。订阅匹配通过现有团购数据完成，命中后使用站内消息提醒（含口碑摘要）。

评价洞察同样「LLM 优先、规则词典兜底」，分析结果写入 `review_analysis` 表，用于商品 / 团购详情的口碑标签展示与提醒摘要增强。因此，本项目已接入可选的大模型解析能力，同时保证**默认不配置任何外部服务也能完整运行**（全部走规则实现）。

## 八、运行条件与主要边界

开发及演示环境按项目说明使用 Java 17、Maven 3.8 及以上、Node.js 18 及以上和 MySQL 8 及以上。部署按一个 Spring Boot 服务和一个 MySQL 数据库考虑，满足本地教学演示规模。

当前方案不包含真实支付、Redis 库存服务、消息队列、微服务拆分、分布式任务平台或外部消息推送。列表分页、移动端适配和多节点扩容属于后续评估事项。
