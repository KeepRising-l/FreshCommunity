# FreshCommunity 需求分析

> **用途**：开题报告 / 任务书「需求分析」章节的素材底稿，同时作为项目的需求全貌总览。
> **口径**：覆盖「已交付 + 计划中」全部需求；与 `openspec/specs/` 基线（9 capability / 35 requirement / 57 scenario）对齐，非功能需求与界面需求为本文件补充完善。
> **日期**：2026-10-13（需求内容变更后请同步维护本文件与 OpenSpec 基线）

## 1. 项目定位与业务闭环

**FreshCommunity —— 社区生鲜团购平台**。以社区为单位，由「团长」发起生鲜商品的限时团购，居民（用户）在线参团下单，在截止时间前达到成团人数即拼团成功，到提货点自提并核销；未达人数则自动解散并全额退款。

业务闭环：

```
团长开团 ──→ 邻居参团下单 ──→ 人数达标成团 ──→ 提货点自提核销
                  │
                  └──→ 截止未达标 ──→ 自动解散 + 全额退款 + 站内通知
```

系统的核心价值与设计重心：

1. **决策驱动**：用户的核心问题是「这个团还差几人、还有多少时间、值不值得跟」，参团进度与截止倒计时是信息主次排列的第一优先级。
2. **状态透明**：团购 3 态、订单 7 态，用户在任何时刻都能知道「现在到哪了、下一步做什么」。
3. **信任建立**：生鲜品类依赖信任——评分前置、提货点常驻、退款承诺明示、评价可追溯。

## 2. 角色与用户需求

### 2.1 角色定义

| 角色 | 定位 | 核心诉求 |
| --- | --- | --- |
| **用户（USER）** | 社区居民，参团购物者 | 快速判断「跟不跟这个团」；订单进展可见；提货凭证清晰 |
| **团长（LEADER）** | 社区提货点经营者，团购发起者 | 开团操作简单；清楚「还差几人」；核销高效不出错 |
| **管理员（ADMIN）** | 平台运营者 | 商品与库存可控；平台运营数据一目了然；异常订单可兜底 |

### 2.2 用户需求（各角色的自然语言诉求）

**用户**：

- UR-1 我能自助注册账号（用户或团长身份），不用等管理员开号
- UR-2 我能一眼看到哪些团快成团了、什么时候截止
- UR-3 我想参团时，下单、支付流程要简单，库存要真实（不能付了钱说没货）
- UR-4 我要随时知道订单进展：付没付上、团成没成、去哪提货、取货码是多少
- UR-5 团没成，钱要能退回；我自己取消订单也要能退款
- UR-6 提完货后我想评价商品和团长，给邻居们一个参考；买之前我也想看看别人的评价

**团长**：

- UR-7 我能快速发起一场团购：选商品、定成团人数与截止时间
- UR-8 我能实时看到我开的团「现在几个人了、还差几个、谁下了单」
- UR-9 邻居来提货时，我要能快速核对取货码完成核销，且不怕重复核销或核销错团

**管理员**：

- UR-10 我能维护商品：上架、改价、改库存、换图片
- UR-11 我能看到平台当日运营概况（订单量、成团量）
- UR-12 遇到投诉纠纷，我能手动为异常订单退款兜底

## 3. 功能需求

> 编号规则：FR-<模块>-<序号>。与实现清单（`docs/implementation-inventory.md`）逐条对应。

### FR-1 用户与权限（user-roles）

系统提供三种角色的注册登录与权限隔离。

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-1-1 | 自助注册 | 用户/团长可自助注册；用户名唯一；BCrypt 存储；团长注册须填提货点；拒绝自助注册管理员；注册即签发 JWT |
| FR-1-2 | 登录与身份识别 | 账号密码登录返回 JWT；登录后系统标识角色；提供当前用户信息接口 |
| FR-1-3 | 角色权限隔离 | 每个角色只能访问对应功能：用户浏览与下单；团长管理自己的团购与核销；管理员商品管理与兜底操作；越权请求被拒绝 |
| FR-1-4 | 团长提货点资料 | 团长资料包含提货点名称与地址；用户浏览团购详情时可见对应提货点 |

### FR-2 商品管理（product-catalog）

管理员维护商品，所有角色可浏览。

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-2-1 | 商品上架 | 字段：名称、价格、库存、图片；缺必填字段拒绝并提示 |
| FR-2-2 | 商品编辑 | 修改名称/价格/库存/图片，结果立即生效（改价后下单金额即用新价） |
| FR-2-3 | 商品浏览 | 商品列表与详情（名称、价格、图片、剩余库存、评分汇总）；支持关键词搜索 |
| FR-2-4 | 商品图片上传 | 单图 ≤5MB；仅管理员可用 |

### FR-3 团购活动（group-buying）

团购活动的创建、参与与判定生命周期。

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-3-1 | 发起团购 | 团长设置参与商品、成团人数、截止时间；截止时间早于当前时间或人数非法则拒绝 |
| FR-3-2 | 参团下单 | 仅进行中的团购可下单；下单生成「待支付」订单；已成团/已解散/已过期的团购拒绝下单 |
| FR-3-3 | 模拟支付 | 收银台确认支付后订单标记已支付、计入团购人数；不对接真实支付渠道，但预留支付服务扩展点 |
| FR-3-4 | 提前成团 | 已支付人数达到成团人数立即成团：关闭下单、为每笔已支付订单生成取货码；并发达标只成团一次 |
| FR-3-5 | 到点解散退款 | 截止时间到仍未成团：团购置「已解散」，全部已支付订单自动全额退款、库存回补；截止后拒绝补单 |
| FR-3-6 | 团长管理自己的团购 | 团长查看自己发起的全部团购、参与人数与订单列表；他人无权查看 |

### FR-4 库存管理（inventory）

商品级库存的扣减与回补，防超卖。

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-4-1 | 下单原子扣减 | 扣减以数据库原子更新实现，并发下单不会超卖（库存=1 时并发下单仅 1 单成功） |
| FR-4-2 | 库存不足拦截 | 购买数量大于剩余库存时拒绝下单并提示 |
| FR-4-3 | 回补库存 | 订单取消、超时关单、团购解散退款时，对应库存回补 |

### FR-5 订单生命周期（order-lifecycle）

订单从创建到终结的全生命周期管理。

**订单状态机**：

```
待支付 → 待成团 → 已成团/待取货 → 已完成
   │         │
   ├→ 已取消 ┘（超时关单 / 用户取消）
   └→ 已退款（解散退款 / 管理员退款）
```

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-5-1 | 状态流转合法 | 状态只能沿合法路径流转，非法变更被拒绝 |
| FR-5-2 | 待成团可取消 | 「待成团」订单用户可主动取消：订单置「已取消」、库存回补、模拟退款 |
| FR-5-3 | 成团后不可取消 | 已成团/已核销订单拒绝用户取消 |
| FR-5-4 | 待支付超时关单 | 创建后 30 分钟未支付：定时任务自动关单、回补库存、不计入团购人数 |
| FR-5-5 | 取货码 | 成团时为每笔已支付订单生成唯一 6 位数字取货码，用户在订单页可见 |
| FR-5-6 | 管理员退款兜底 | 管理员可将异常订单手动标记「已退款」；终态订单拒绝重复退款，退款回退人数与库存 |

### FR-6 提货核销（pickup-verification）

团长对已成团订单的提货核销。

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-6-1 | 输码核销 | 团长在核销页输入 6 位取货码，有效码对应订单置「已完成」；无需扫码设备 |
| FR-6-2 | 防重复核销 | 已核销的取货码不能再次核销 |
| FR-6-3 | 仅限本团订单 | 团长只能核销自己名下团购的订单，跨团取货码无效 |

### FR-7 数据看板（admin-dashboard）

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-7-1 | 今日订单数 | 展示当日 0 点至当前时间创建的订单总数 |
| FR-7-2 | 今日成团数 | 展示当日判定为「已成团」的团购总数 |
| FR-7-3 | 看板扩展（计划） | 成交额、注册用户数、7 日趋势、订单状态分布（设计稿已预留，待实施） |

### FR-8 评价体系（reviews）

已完成提货的用户对商品与团长做出评价，形成口碑数据。

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-8-1 | 评价资格 | 仅「已完成」（已核销）订单可评价；一单一评；其他状态订单与重复评价被拒 |
| FR-8-2 | 评价内容 | 商品评分与团长评分（1–5 整数）必填；文字评论可选（≤500 字符） |
| FR-8-3 | 订单页入口 | 「我的订单」中已完成且未评价订单展示「去评价」入口；评价后显示「已评价」 |
| FR-8-4 | 评分汇总 | 商品与团长各自汇总平均分（保留一位小数）与条数；无评价时不展示 0 分误导 |
| FR-8-5 | 评价可见性与只读 | 商品详情向所有登录用户展示评价列表；评价提交后只读，不可被他人修改删除 |

### FR-9 站内消息（notifications）

订单生命周期关键节点自动生成站内信。

| 编号 | 功能需求 | 要点 |
| --- | --- | --- |
| FR-9-1 | 团购结果通知 | 成团时通知该团各订单用户「已成团、待提货」；解散时通知「未成团、已全额退款」 |
| FR-9-2 | 订单状态变更通知 | 待支付超时关单、核销成功、管理员退款三类事件各生成一条通知 |
| FR-9-3 | 消息仅本人可见 | 用户只能读取和操作自己的消息，越权操作被拒 |
| FR-9-4 | 未读计数与标记已读 | 提供未读数与入口角标；支持单条已读与一键全部已读 |

## 4. 非功能需求

> 本节为现有规格（OpenSpec）之外的补充完善，面向开题报告「非功能需求」小节。

### NFR-1 安全性

- **认证**：JWT 无状态鉴权，除登录/注册/健康检查外全部接口需要有效 token
- **密码存储**：BCrypt 哈希（`$2a$10$`），任何接口不返回密码字段
- **权限控制**：Spring Security 注解式角色鉴权（`@PreAuthorize`）+ 数据归属校验（团长只能操作自己的团购、用户只能操作自己的订单与消息）
- **注入防护**：MyBatis 参数化查询，无拼接 SQL
- **上传控制**：仅管理员可上传，限制图片类型与 5MB 大小

### NFR-2 一致性与可靠性

- **防超卖**：库存原子扣减（`UPDATE ... WHERE stock >= n`），并发安全（实测：库存 1 时 8 个并发请求仅 1 单成功）
- **防重复成团**：成团判定使用条件更新，并发支付同时达标时只成功一次
- **事务一致性**：状态变更与通知、库存回补在同一数据库事务内完成
- **幂等守卫**：终态订单拒绝退款/取消等重复操作；重复退款实测被拒且库存不重复增长
- **定时兜底**：@Scheduled 每分钟扫描到期团购、超时订单，容忍 ≤1 分钟处理延迟

### NFR-3 性能与容量

- **部署形态**：单体应用单机部署（后端 8080 + MySQL），满足教学演示与小型社区规模
- **响应时间**：常规接口毫秒级（本地实测）
- **已知取舍**：列表无分页（当前数据规模小，作为演进项）；前端主包约 1.27MB（Element Plus 全量引入，未做按需）

### NFR-4 易用性

- **角色自适应导航**：三种角色各自独立的菜单分组，互不干扰
- **状态可视化**：7 种订单状态采用统一徽章体系 + 5 节点时间轴；金额、进度、取货码使用等宽数字
- **完整反馈**：列表页具备加载骨架、空状态与错误重试三态
- **中文界面**：全中文文案与错误提示，无英文占位符

### NFR-5 可维护性

- **规格驱动开发**：需求先于实现，全部功能有 OpenSpec 提案与验收场景（9 capability / 35 requirement / 57 scenario，2 个变更已归档）
- **分层架构**：Controller / Service / Mapper 分层，统一响应格式 `{code, msg, data}`
- **自动化测试**：30 个后端集成测试用例（真实 Spring 上下文 + MockMvc + 独立测试库），每个修复缺陷均转化为回归用例
- **统一代码规范**：Lombok、MyBatis-Plus 自动填充、状态常量集中定义

### NFR-6 可扩展性

- **支付扩展点**：`PayService` 接口隔离支付实现，对接真实支付（如微信支付）只需新增实现类
- **消息类型可扩展**：通知类型以枚举管理，新增事件类型无需改表
- **看板预留**：数据看板接口与设计稿预留扩展位（成交额、趋势、状态分布）
- **界面分期落地**：设计系统与公共组件已完成，后续页面按设计稿渐进替换

### NFR-7 兼容性

- **运行环境**：Java 17、MySQL 8+、Node.js 18+
- **浏览器**：现代浏览器（Chrome / Edge）桌面端；移动端响应式适配为规划项（<768px 断点）

## 5. 关键业务流程（用例）

> 从 57 条验收场景中提炼的主干用例，用于开题报告「业务流程」与答辩演示脚本。

**UC-1 参团到提货（主链路）**
用户浏览团购广场 → 打开团购详情（看进度/倒计时/提货点）→ 选择数量下单 → 模拟支付（计入团人数）→ 人数达标成团（生成取货码 + 站内通知）→ 用户到订单页查看取货码 → 到提货点，团长输码核销 → 订单已完成 → 用户评价商品与团长。

**UC-2 支付即达标（提前成团）**
某团已支付人数为 N−1，用户支付第 N 单 → 支付事务内同步判定达标 → 团购立即成团、关闭下单、全部已支付订单生成取货码，各自用户收到成团通知。

**UC-3 到点未成团（自动解散）**
团购到达截止时间仍未达标 → 定时任务判定解散 → 全部已支付订单转「已退款」、库存回补、人数回退 → 各订单用户收到解散退款通知；截止后补单被拒。

**UC-4 订单取消（用户侧退款）**
待成团订单用户点击取消 → 订单置「已取消」、库存回补、团购人数递减 → 不再产生虚假成团。

**UC-5 超时关单**
用户下单后 30 分钟未支付 → 定时任务关闭订单、回补库存（不计入团人数）→ 用户收到关单通知。

**UC-6 提货核销**
团长在核销台输入 6 位取货码 → 系统校验「码存在、属于本团、未核销」→ 订单置「已完成」→ 用户收到提货完成通知；重复核销与跨团核销均被拒绝。

**UC-7 管理员退款兜底**
用户投诉 → 管理员对订单执行手动退款 → 订单置「已退款」（终态订单拒绝）、库存与人数回退、用户收到退款通知。

## 6. 需求边界（做什么 / 明确不做）

**明确不做（已在规格与实现中一致排除）**：

- 真实支付（模拟实现，通过 `PayService` 接口预留扩展点）
- 商家入驻、配送/骑手、佣金结算
- 限购、优惠券、秒杀
- 评价审核 / 敏感词过滤 / 评价修改删除 / 团长回复评价
- 短信 / 邮件 / App 推送等外部通道（站内信即站内可见）
- WebSocket 实时推送（未读数按页面加载拉取）
- 消息分类开关、免打扰设置
- App / 小程序（移动端为响应式 Web，非原生）

**计划中（本文件纳入需求，实现清单标注为待实施）**：FR-7-3 看板扩展、FR-10-3 团长端界面、FR-10-4 管理端界面、FR-10-5 响应式移动端。
