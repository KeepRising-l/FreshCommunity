### Q1: 并发扣减库存为什么用 MySQL 原子更新，而不是 Redis + Lua 分布式锁？

**导师可能提问**：
> “做电商秒杀或团购通常都用 Redis 做预扣减，你为什么直接在 MySQL 里扣库存？能抗住并发吗？不会超卖吗？”

**满分回答**：
> “老师您好，这是一个非常关键的技术选型取舍。
> 1. **正确性保证**：我们采用的是数据库行级排他锁的原子扣减语句：`UPDATE product SET stock = stock - #{qty} WHERE id = #{id} AND stock >= #{qty}`。MySQL InnoDB 引擎在执行该更新时，会自动对该商品行记录加 `X` 锁（排他写锁），并且由 `WHERE stock >= #{qty}` 保证了扣减条件。如果多个请求同时到达，InnoDB 会进行行锁排队串行化扣减，受影响行数为 0 时后端立即识别并拒绝下单，**在数据库事务级别有效防止了超卖（Overselling）**。我们在 `OrderConcurrencyApiTest` 中编写了 8 线程并发抢购单件库存的集成测试（`eightThreadsCompeteForLastSingleStockOnlyOneSucceeds`），实测仅 1 单返回 200 成功、7 单返回 400 被拦截，最终库存严格为 0。
> 2. **架构复杂度权衡**：如果引入 Redis + Lua 做预扣，虽然吞吐量更高，但会引入分布式事务、缓存与数据库最终一致性、Redis 挂掉时的数据恢复以及库存回补对账等额外链路，对于社区生鲜团购这种中小型场景来说过度设计，增加了部署运维复杂度。
> 3. **生产演进方案**：如果未来业务量达到数万 QPS 的秒杀级别，我们可以基于现有代码平滑演进：在应用层前置增加 Redis Lua 脚本原子扣减做第一道屏障，异步通过 RocketMQ / RabbitMQ 削峰落库。”

### Q2: 大模型 API 调用可能出现超时、断网或欠费，系统如何保证高可用？

**导师可能提问**：
> “你的系统接入了大模型做 AI 导购和评价洞察，但外部大模型服务是不可控的，如果外部 API 报错或者超时，整个系统是不是就卡死了？”

**满分回答**：
> “老师抓得很准。在设计 AI 导购模块时，高可用与服务降级是我们优先考虑的原则：
> 1. **分级降级策略（LLM 优先 + 规则词典兜底）**：
>    - 在**需求订阅解析**上，系统首先尝试调用 OpenAI 兼容协议的大模型将自然语言（如‘十块钱以内的苹果’）映射到在售商品名和价格上限；但同时我们在 `RuleDemandParseService` 中实现了一套基于分词与正则的本地规则词典。当未配置 API Key、网络超时（默认 5 秒熔断）或响应异常时，代码会自动捕获异常并静默回退到本地规则解析，**确保在无网络或无外部 Key 的离线环境下系统 100% 演示可用**。
>    - 在**评价情感与标签分析**上，定时任务同样采用‘LLM + 规则词典兜底’，词典按长词优先匹配，确保即使无外部服务也能从评论中提取‘新鲜’、‘实惠’等口碑标签。
> 2. **真实响应原则（宁缺毋滥，绝不伪造）**：
>    - 在**即时推荐（问 AI）**这种强依赖大语言模型推理的场景下，若大模型接口不可达，系统会诚实、清晰地返回友好提示‘AI 导购服务暂时不可用，请稍后再试’，并引导用户去团购广场自主选购，**坚决不返回虚假推荐数据**误导消费者。
> 3. **超时与线程安全控制**：所有 WebClient / RestClient 请求均配置了严格的 Connection Timeout 与 Read Timeout，防止外部长延迟耗尽后端的 Tomcat 线程池。”

### Q3: 为什么提货要用 6 位取货码？如何防范暴力猜测与重复核销？

**导师可能提问**：
> “提货为什么要生成取货码？为什么是 6 位纯数字？6 位数字只有 100 万种可能，别人随便猜一个不就能冒领了吗？”

**满分回答**：
> “1. **业务场景匹配**：在社区生鲜团购场景中，用户到楼下便利店或自提点取货时，6 位数字是最符合人类记忆和口头报码体验的长度（类似于菜鸟驿站的取件码）。如果用 32 位 UUID，无论是买家念给团长还是团长在手机/电脑键盘上敲入，交互成本都极高。
> 2. **安全防护机制（四重已实现防线，均通过自动化测试验证）**：
>    - **第一重：加密级随机数 + 数据库唯一索引**：取货码使用 Java 的 `SecureRandom` 生成，并由 `order` 表上的 `uk_order_pickup_code` 唯一索引在数据库层保证全局不重复（若并发碰撞抛出 `DuplicateKeyException` 则自动重试生成）。
>    - **第二重：归属强校验（仅限本团）**：团长在核销时，后端会校验 `groupBuy.getLeaderId().equals(leaderId)`。这意味着即使有人猜到了某个取货码，如果该订单不是在当前团长的提货点成团的，系统会直接报错拒绝，无法跨团冒领。
>    - **第三重：状态机单向条件更新（防重复核销）**：订单必须处于 `SUCCESS`（或历史兼容状态 `PENDING_PICKUP`）待取货状态，核销时通过条件更新 `UPDATE \`order\` SET status = 'COMPLETED' WHERE id = #{id} AND status = #{expectedStatus}` 原子推进到 `COMPLETED`，一旦核销立即作废，杜绝并发一码多用。
>    - **第四重：核销失败频次限流（防暴力枚举）**：在 `OrderService.verifyPickupCode` 中内置了 5 分钟滑动窗口防暴力枚举保护——同一团长连续输错 5 次取货码后自动触发 5 分钟临时锁定（拒绝后续请求并返回 `"核销失败次数过多，请稍后再试"`），核销成功则重置计数，在 `LeaderConsoleApiTest#verifyPickupCodeRateLimitsBruteForceAttempts` 中已通过自动化测试验证。”

### Q4: 订单状态机有哪 7 种状态？如何避免并发操作导致“虚假成团”？

**导师可能提问**：
> “你的系统里订单有哪几种状态？假如还差 1 个人成团，同时有 2 个人支付成功，系统会发生什么？会不会成团两次或者人数算错？”

**满分回答**：
> “1. **7 种严格状态**：
>    - `PENDING_PAYMENT`（待支付）
>    - `PENDING_GROUP`（待成团）
>    - `SUCCESS` / `PENDING_PICKUP`（已成团/待取货）
>    - `COMPLETED`（已完成）
>    - `CANCELLED`（已取消）
>    - `REFUNDED`（已退款）
> 2. **团购行锁 + 不同支付用户去重计数 + CAS 成团判定**：
>    - 当用户模拟支付时，首先通过 `groupBuyMapper.lockOpenGroup` 锁住仍在进行且未过截止时间的团购行，并检查该用户在该团下是否已有 `PENDING_GROUP` 订单（**同一用户多笔已付订单只计 1 人**）。若为首次参团，则执行：
>      `UPDATE group_buy SET member_count = member_count + 1 WHERE id = #{id} AND status = 'ONGOING' AND deadline > NOW()`
>    - 随后调用 `trySuccess` 方法：
>      `UPDATE group_buy SET status = 'SUCCESS' WHERE id = #{id} AND status = 'ONGOING' AND member_count >= target_count`
>    - 由于团购行锁与条件更新配合，**并发支付达标时只会触发一次成团状态切换**，将所有 `PENDING_GROUP` 订单更新为 `SUCCESS`、逐单生成唯一 6 位取货码并发送成团站内信；而已成团后其余未支付（`PENDING_PAYMENT`）订单将不能再支付，但可以取消并回补库存。”

### Q5: 用户取消待成团订单时，为什么必须同步回退 member_count？

**导师可能提问**：
> “订单取消的时候直接把订单状态改成 CANCELLED 不就行了吗？为什么一定要把 group_buy 的 member_count 减 1？”

**满分回答**：
> “这是一个非常经典的**状态一致性陷阱**：
> 1. 如果取消订单只改订单自身状态而不回退 `group_buy.member_count`，那么团购表里记录的‘已参团人数’就会产生虚增；
> 2. 假设目标成团人数是 3 人，A、B 参团（此时人数为 2），A 随后反悔取消订单，若不减人数，表里依然是 2；当 C 参团时人数变成 3，系统就会误判为‘拼团成功’并提前关团发提货码！但实际上真实有效订单只有 B 和 C 两个人，造成了**‘虚假成团’（Phantom Group Success）**，导致提货现场商品严重不足、账目与实物对不齐。
> 3. 同时，我们按**不同的已支付用户数**统计 `member_count`（同一买家下多单只算 1 人）。在 `OrderService.cancelOrder` 和管理员退款中，我们将‘修改订单状态’、‘调用模拟退款 `PayService.refund`’、‘当该用户在该团下已无其他待成团订单时回退 `member_count`（原子 -1）’以及‘回补商品库存’放在同一个数据库本地事务（`@Transactional`）中；若模拟退款失败，整个事务自动回滚，保证状态、人数与库存一致。”

### Q6: 60 秒定时任务如果执行耗时超标怎么办？多节点分布式下如何防重复？

**导师可能提问**：
> “你系统里用 `@Scheduled(fixedRate = 60000)` 每分钟跑一次团购到期处理和未支付关单，如果单次跑了 70 秒会发生什么？如果部署两个后端实例，会不会把一笔订单退款退两次？”

**满分回答**：
> “1. **单机并发执行机制**：
>    - Spring Boot 的 `@Scheduled` 默认是基于单线程任务调度器的。如果前一次执行超过 60 秒，后一次触发会被推迟到前一次彻底完成后才开始，不会发生同节点上的任务自我重叠。
>    - 同时我们在每个定时方法内部做了批处理防长耗时设计，只捞取必要的数据。
> 2. **分布式环境防重设计（幂等性与分布式锁）**：
>    - **第一道防线：状态机幂等条件更新**。定时任务在解散团购或关闭订单时，执行的 SQL 都是条件更新，如 `UPDATE order SET status = 'REFUNDED' WHERE id = #{id} AND status = 'PENDING_GROUP'`。如果节点 A 已经退款了，节点 B 查到或执行时受影响行数就是 0，天然具备幂等性，不会产生二次退款。
>    - **第二道防线：分布式调度演进**。在单体毕设架构中，本地 `@Scheduled` 足以满足功能验证；如果上线多副本生产环境，可以引入 **ShedLock**（基于 MySQL/Redis 锁表的轻量级分布式定时任务锁）或 **XXL-JOB** 统一调度中心，确保同一时刻全集群只有一个节点执行定时任务。”

### Q7: JWT 无法主动注销怎么办？如果要在生产环境落地该如何改进？

**导师可能提问**：
> “你用的 JWT 是无状态的，用户点击‘退出登录’后，前端清除了 token，但如果黑客拿到了原来的 token，在过期前依然可以访问接口，你怎么解决？”

**满分回答**：
> “1. **毕设架构选型理由**：
>    - 本系统选型无状态 JWT，核心目标是保持服务端的无状态性（Stateless），降低对外部会话存储的依赖，系统启动即可运行。
> 2. **生产级解决方案（三步走）**：
>    - **方案一：短 Token + Refresh Token（双令牌机制）**。将 Access Token 的有效期缩短为 15 分钟，降低泄漏后的暴露窗口；同时配合 7 天有效期的 Refresh Token 存入 HttpOnly Cookie，刷新时校验有效性。
>    - **方案二：Redis 黑名单机制**。用户点击退出登录或修改密码时，将当前 Token 的唯一签名或 JTI（JWT ID）写入 Redis 黑名单，过期时间设置为该 Token 的剩余有效时长；在 `JwtAuthenticationFilter` 过滤器中前置查一次 Redis，命中黑名单则直接返回 401。
>    - **方案三：用户版本号 / 密码变更时间戳**。在用户表增加 `token_version` 字段，JWT Payload 中携带该版本号。每次用户改密或强制下线时自增版本号，校验时若 Payload 中的版本号低于数据库版本号则失效。”

### Q8: 消息实时推送为什么选用 SSE，而不是双向的 WebSocket？

**导师可能提问**：
> “实时消息推送大家一般都用 WebSocket，你为什么选择 SSE（Server-Sent Events）？它有什么区别？”

**满分回答**：
> “1. **单向推送的业务契合度**：
>    - 我们的场景是‘团购结果变更、核销完成、AI 匹配命中提醒’等**由服务端单向推向浏览器**的业务通知，客户端不需要通过长连接向服务器频繁回传数据（用户的所有操作如参团、支付、查询都是标准的 RESTful HTTP 接口）。
> 2. **技术对比与协议优势**：
>    - **基于 HTTP 协议**：SSE 基于标准 HTTP/1.1 与 HTTP/2 协议，长连接走文本流（`text/event-stream`），完全兼容公司和校园网现有的反向代理（如 Nginx）、负载均衡和防火墙，天然无需像 WebSocket 那样进行协议升级握手（HTTP Upgrade），也不会被某些中间路由拦截。
>    - **轻量且自带重连**：浏览器端使用 W3C 原生规范的 `EventSource` API，代码仅需几行；且原生支持断线自动指数退避重连，连接恢复后自动同步最新未读数。
>    - 因此，在‘服务端单向通知’的架构定位下，**SSE 比 WebSocket 更加轻量、稳定、易调试和低开销**。”

### Q9: 什么是 OpenSpec 规范驱动开发？它比传统先写代码后补文档好在哪？

**导师可能提问**：
> “你的项目目录里有一个 openspec 文件夹，包含了 12 个 capability 和很多变更记录，这是什么意思？它是怎么指导你开发的？”

**满分回答**：
> “1. **什么是规范驱动开发（Specification-Driven Development）**：
>    - 传统软件开发往往是‘想到哪写到哪，写完代码再去补开题报告和设计文档’，导致文档与代码严重脱节。
>    - 本项目引入了 **OpenSpec** 规范驱动开发范式：在开发每一个功能前，先在 `openspec/changes/` 下编写形式化的提案（`proposal.md`）、技术架构决策（`design.md`）、明确的验收场景（`specs/*.md`，采用 Gherkin 风格的 GIVEN-WHEN-THEN 语义）和任务清单（`tasks.md`）。
> 2. **带来的核心收益**：
>    - **需求确定性**：开发前明确系统边界（明确做什么、明确不做什么），避免边做边改需求。
>    - **高覆盖率测试**：每一个需求验收场景（Scenario）都能一一对应地翻译为后端的自动化测试用例。项目中 19 个测试类的 132 个后端自动化测试用例正是根据 OpenSpec 规格与回归场景直接编写出来的。
>    - **文档即代码**：功能验收通过后将变更归档合并到主基线，实现了‘代码与文档同步演进’，这为撰写毕业论文提供了无可挑剔的真实过程素材。”

### Q10: 管理员退款如果发生在订单已核销之后，系统是如何拦截的？

**导师可能提问**：
> “管理端有一个退款兜底入口，如果某个买家已经在团长那里提完货核销成功了，管理员手滑又去点退款，系统会不会把钱退了、库存还加回去？”

**满分回答**：
> “**绝对不会发生**。
> 1. **状态机终态守卫（State Guard）**：
>    在后端的 `OrderService.refundOrderByAdmin` 中，执行的第一步就是状态终态断言：
>    ```java
>    if ("COMPLETED".equals(order.getStatus()) || "REFUNDED".equals(order.getStatus())) {
>        throw new IllegalStateException("订单已完成或已退款，不可重复退款");
>    }
>    ```
> 2. **数据库级条件更新（防并发手抖）**：
>    更新状态时，SQL 语句强制带上旧状态校验：
>    `UPDATE \`order\` SET status = 'REFUNDED' WHERE id = #{id} AND status NOT IN ('COMPLETED', 'REFUNDED')`
>    如果受影响行数为 0，说明该订单已被其他人处理或已完成提货，事务立即回滚，后续的库存回补和退款通知根本不会触发。我们在 `GroupBuyFlowApiTest` 中有专门的测试用例验证此边界，实测 100% 拦截。”

### Q11: 为什么拼团价不直接存在 group_buy 表，而要单独搞一张 group_buy_item？

**导师可能提问**：
> “你的 group_buy 表里只有成团人数和截止时间，为什么没有存商品 ID 和拼团价？这样查团购不是还要关联一张表吗？”

**满分回答**：
> “1. **快照解耦（Snapshot Isolation）**：
>    - 在生鲜电商中，商品的基本价格（零售价）是会随市场波动频繁变动的。团长开团时的拼团价是一个‘历史价格承诺’，必须固化下来，不能因为商家日后修改了商品价格而导致已经开团或已支付订单的金额发生漂移。
> 2. **数据模型扩展性（多商品团购预留）**：
>    - 现实中的社区团购经常有‘家庭生鲜蔬菜组合包’或‘多选一拼团’活动，即一个团购活动包含多个商品。
>    - 如果把 `product_id` 和 `price` 写死在 `group_buy` 主表上，未来只要业务扩展为‘一团多品’，整个数据库表结构和实体都要重构；而拆分出 `group_buy_item`（团购明细快照表），主表负责团购生命周期（人数、状态、截止时间），明细表负责挂载商品与价格快照，**符合数据库规范化第三范式（3NF），并且为系统未来扩展多品团购留出了完美的架构弹性**。”

### Q12: 数据库设计中，为什么要用反引号将 order 表名括起来？

**导师可能提问**：
> “我看你的代码里 `@TableName("`order`")` 特意加了反引号，如果不加会发生什么？”

**满分回答**：
> “1. **原因分析**：
>    - 在 SQL 标准以及 MySQL 数据库中，`ORDER` 是一个保留关键字（用于 `ORDER BY` 排序子句）。
>    - 如果不加反引号，MyBatis-Plus 或手写 SQL 生成的语句类似于 `SELECT * FROM order WHERE ...`，MySQL 语法解析器会把 `order` 误当成排序关键字，从而抛出致命的 `SQLSyntaxErrorException`（语法错误）。
> 2. **工程规范**：
>    - 在生产和规范设计中，通常可以通过加表前缀（如 `t_order` 或 `fc_order`）来彻底避开关键字冲突；
>    - 在当前项目中，实体类注解中显式声明 `@TableName("`order`")`，强制在生成的 SQL 语句中带有转义反引号，既保留了清晰的领域对象命名，又确保了数据库执行的 100% 语法安全性。”
