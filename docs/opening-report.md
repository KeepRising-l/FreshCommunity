## 一、选题背景与意义

社区团购是近年生鲜零售领域快速发展的模式，其信息系统具有鲜明的业务特殊性。本节从选题背景与选题意义两个方面进行说明。

### 1.1 选题背景

社区团购是近年生鲜零售领域发展最快的模式之一：以居住社区为单位，由「团长」（社区提货点经营者）发起生鲜商品的限时团购，居民集中下单、到社区提货点自提。该模式凭借「以销定采降低损耗、社区自提降低履约成本、邻里信任降低获客成本」的结构性优势，已成为生鲜零售的重要渠道，并催生了大量区域性平台与创业项目。

与传统 B2C 商城相比，社区团购系统在业务与技术上都具有鲜明特殊性：

1. **「成团」机制是交易成立的前提**——一笔订单能否成交，取决于截止时间前参团人数是否达到成团人数；系统必须同时管理「人数」与「时间」两个维度，并正确处理达标成团、到点解散、全额退款三条分支；
2. **并发与一致性要求高**——商品库存有限、团购限时，多用户并发下单场景真实存在，系统必须防止超卖，并保证订单、库存、团购人数三者一致（例如取消订单时必须同步回退人数，否则会产生「虚假成团」）；
3. **多角色协作闭环**——用户、团长、管理员围绕同一笔交易协作，涉及开团、参团、核销、退款等跨角色流程，权限与状态流转必须清晰严谨。

在技术层面，Spring Boot + Vue 的前后端分离架构已是国内 Web 应用开发的主流选择；同时，大语言模型（LLM）技术在垂直场景的落地成为新的应用热点，如何把 LLM 能力嵌入真实的业务链路（而非做成孤立演示），是值得探索的工程实践问题。

### 1.2 选题意义

**应用价值**：本课题完整实现社区团购「开团 → 参团 → 成团 → 提货核销」交易闭环与三角色管理能力，是一个功能完整、可直接运行的系统，可作为教学案例与区域社区团购系统的原型。

**技术价值**：课题覆盖多个有代表性的工程问题——数据库原子操作实现并发库存控制、状态机建模与守卫、定时任务驱动的到期判定、数据一致性的对称设计；并引入 AI 导购能力，探索「自然语言需求订阅 + 主动匹配提醒」这一 LLM 垂直场景的落地方式。

**方法价值**：课题全程采用规格驱动开发（OpenSpec）方法：需求先于实现，每个功能都有可追溯的提案、验收场景与实测验证记录，是软件工程方法论的一次完整实践。

## 二、国内外研究现状

**行业现状**：社区团购自 2016 年前后兴起，2020 年后进入规模化竞争阶段。主流平台以微信生态为主要入口（群内分享 + 小程序下单），业务高度依赖「团长运营 + 次日自提」的履约结构。行业系统的共性技术诉求集中在：高并发下的库存准确、拼团状态的实时同步、退款时效与资金安全。

**系统实现现状**：现有社区团购类系统的实现方案以「前后端分离 Web 应用 + 关系型数据库」为主流架构；多数文献与项目聚焦于通用电商能力（商品、订单、支付），对社区团购特有的「成团判定、人数一致性、自动解散退款」机制的系统性设计讨论相对有限；此外，将 LLM 能力与交易链路深度结合的公开实践仍处于早期阶段，多见于营销文案生成、客服问答等边缘场景。

**本课题的定位**：聚焦「成团机制正确性」与「交易数据一致性」两个社区团购的特有工程问题做系统性设计，并探索 AI 导购（需求订阅与主动提醒）与交易链路的结合方式，形成可运行、可验证的完整实现。

## 三、研究内容与目标

围绕社区团购的完整业务闭环，本课题的研究目标与主要研究内容如下。

### 3.1 研究目标

设计并实现一个社区生鲜团购平台，完整支撑「用户 / 团长 / 管理员」三种角色围绕团购交易的全流程协作，重点保证：**成团判定准确、并发下单不超卖、订单状态流转严谨、异常场景（未成团、超时、退款）处理完整**；并实现 AI 导购特色能力。

### 3.2 主要研究内容

1. **用户与权限**：三角色注册登录、JWT 鉴权、角色权限隔离与数据归属控制；
2. **商品与库存**：商品维护与图片上传；研究**并发安全的库存扣减与回补机制**（防超卖）；
3. **团购生命周期**：团长开团（成团人数 + 截止时间）、用户参团与模拟支付、**人数达标提前成团**、**截止未达标自动解散退款**；
4. **订单管理**：**订单状态机设计**（7 状态与合法流转路径）、待支付超时关单、取货码生成与核销、管理员退款兜底；
5. **评价与消息**：已核销订单的双维度评价与评分汇总；订单全生命周期站内消息；
6. **AI 导购（特色）**：**自然语言需求订阅**（解析 → 匹配 → 主动提醒）与解析降级设计；
7. **系统设计与文档**：需求分析、系统设计说明书、界面设计与原型、测试与验证报告。

## 四、技术路线与实施方案

本课题采用前后端分离的主流技术栈，并以规格驱动的方式组织开发。以下从技术选型、系统架构、关键机制与开发方法四个方面说明。

### 4.1 技术选型

| 层 | 技术 |
| --- | --- |
| 后端 | Spring Boot 3 + Spring Security（JWT）+ MyBatis-Plus |
| 数据库 | MySQL 8（事务 + 行锁支撑并发控制） |
| 前端 | Vue 3 + Vite + Element Plus + Pinia |
| AI 能力 | OpenAI 兼容大模型接口（可插拔）+ 规则解析降级 |
| 工程方法 | OpenSpec 规格驱动开发 + 集成测试与实测验证 |

### 4.2 系统架构

采用前后端分离的分层单体架构：浏览器（Vue SPA）→ HTTP `/api`（JWT 鉴权）→ Spring Boot（Controller → Service → Mapper）→ MySQL；另有定时任务组件以 60 秒周期执行「到期团购判定」与「超时关单」扫描。架构图与详细设计见《系统设计说明书》。

### 4.3 关键机制方案

| 问题 | 方案 |
| --- | --- |
| 并发防超卖 | 数据库原子扣减（`UPDATE ... WHERE stock >= n`），影响行数为 0 即拒绝 |
| 防重复成团 | 团购状态条件更新（期望状态作为更新条件），并发达标仅生效一次 |
| 数据一致性 | 人数与库存的「支付 +1 / 取消 −1 / 退款 −1」对称回补设计 |
| 超时与到期处理 | @Scheduled 定时扫描 + 支付事务内提前判定双路径互补 |
| AI 解析可靠性 | 大模型优先、规则兜底的可降级解析链；订阅匹配复用站内消息通道 |

### 4.4 开发方法（规格驱动）

采用 OpenSpec 规格驱动流程：`提议（提案 / 验收场景）→ 评审 → 实施（任务清单）→ 验证（实测断言）→ 归档（基线同步）`。每个功能在实现前先与验收场景对齐，完成后以对真实运行系统的断言作为完成标准；修复缺陷同步补充回归测试。

## 五、可行性分析

**技术可行性**：所选技术栈（Spring Boot / Vue / MySQL）均为成熟主流方案，学习资料充分；核心难点（并发防超卖、状态机、定时任务）已有明确可行的技术方案并通过原型验证（并发测试、回归测试均已通过）。

**经济可行性**：开发与运行环境均为免费开源软件，本地单机即可完成开发、测试与演示；不依赖付费服务（AI 解析支持无外部服务降级运行）。

**操作可行性**：系统为浏览器访问的 Web 应用，三种角色界面操作直观；演示环境可一键初始化（建库脚本 + 演示数据集）。
