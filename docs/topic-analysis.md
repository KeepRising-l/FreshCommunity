# FreshCommunity 毕业设计选题分析

> **课题名称**：社区生鲜团购平台的设计与实现
> **项目名称**：FreshCommunity
> **课题类型**：应用开发型
> **整理日期**：2026 年 10 月 14 日

## 一、选题说明

本课题围绕社区生鲜团购业务，设计并实现一个面向社区居民、团长和平台管理员的 Web 系统。系统主流程是：团长发布限时团购，用户参团并模拟支付；人数达到成团要求后，团购成功并生成取货码，用户到提货点自提，由团长核销；到期仍未达到人数时，系统解散团购并办理模拟退款。

项目重点是把团购规则落实为可执行的系统流程，并保证订单、库存、参团人数和通知在不同业务结果下保持一致。课题属于软件工程应用实践，不以提出新的通用算法或商业运营理论为目标。

## 二、选题背景与问题分析

社区团购把线上下单、按人数成团和社区自提结合在一起，业务规则比普通商品列表销售多了时间和人数条件。同一商品可能关联多个团购，用户的订单还要经过支付、成团、取货或退款等状态变化。系统需要处理以下问题：

1. **成团判定依赖时间和人数**：系统要按有效支付人数判断是否达标，也要在截止时间到达时及时处理未成团活动。
2. **订单与库存需要同步变化**：下单时要扣减库存；取消、超时关单或退款时要回补库存。多用户同时下单时，不能因并发请求导致超卖。
3. **团购人数必须反映有效订单**：取消或退款后要相应减少参团人数，避免无效订单仍被计入成团条件。
4. **多个角色共同完成一笔交易**：用户负责参团，团长负责开团和提货核销，管理员负责商品维护和异常退款。各角色只能访问获准的数据和操作。
5. **异常与重复操作需要有明确结果**：重复退款、重复核销、超时支付和团购截止等情况都需要状态检查，避免重复执行造成数据错误。

这些问题适合用一个边界清楚的系统进行分析和验证：既能呈现完整业务，又能围绕库存并发、状态流转和权限控制开展设计与测试。

## 三、选题目的与意义

### 3.1 应用目的

完成一个可本地运行和演示的社区生鲜团购平台，覆盖用户、团长和管理员三类角色，呈现从开团到自提核销以及未成团退款的主要流程。真实支付、商家入驻和配送调度不纳入本期实现范围。

### 3.2 工程实践意义

课题将需求分析、系统分层、数据库设计、接口实现和验证过程结合起来，重点落实库存原子扣减、订单状态守卫、团购条件更新、定时任务和数据归属检查等工程措施。每项关键规则都可以映射到业务场景和验证记录，便于说明设计决定及其效果。

### 3.3 教学与应用价值

项目可用于展示前后端分离 Web 系统的开发过程，以及角色权限、事务处理、状态流转和异常场景的处理方式。系统作为教学和毕业设计原型使用，不对生产级容量、真实支付或实际物流履约作出承诺。

## 四、研究目标

1. 梳理三类角色的业务目标、功能需求、权限范围和非功能要求。
2. 设计商品、团购、订单、库存、评价、消息等模块及其数据关系。
3. 实现团购创建、参团下单、模拟支付、成团或解散、取货码核销、评价和站内消息等业务流程。
4. 使用数据库事务、原子更新和状态条件检查，维护库存、订单状态与参团人数的一致性。
5. 通过接口测试和业务场景验证检查主要流程、异常处理、权限边界及并发下单行为。
6. 对 AI 导购订阅功能完成构建、接口和页面走查；大语言模型解析作为后续扩展，当前系统使用规则解析。

## 五、主要研究内容

| 研究内容 | 具体工作 |

| 交易与一致性 | 实现待支付、待成团、已成团、待取货、已完成、已取消、已退款等状态流转；处理库存扣减与回补 |

| 系统验证 | 围绕正常交易、超时、未成团、并发下单、越权及重复操作设计检查场景 |

## 六、研究方法与实施路线

本课题采用需求分析、结构化设计、迭代实现和场景验证相结合的方式。项目使用 OpenSpec 管理部分需求规格和变更；功能实现状态及验证证据以实现清单和验证报告为准。

```text
业务与角色分析
      ↓
需求规格与系统设计
      ↓
前后端分层实现和数据库设计
      ↓
接口、状态流转、并发和权限检查
      ↓
问题修复、文档整理和毕业论文撰写
```

关键技术路径包括：用 MySQL 条件更新完成库存原子扣减；用带预期状态的更新限制成团、退款和核销的重复执行；用事务维护业务数据；用定时任务处理到期团购和超时未支付订单。验证结论只依据实际运行记录，不把尚未执行的测试写成通过。

## 七、课题特色与成果定位

课题的特色在于聚焦社区团购交易中的具体工程问题，并将其转成系统规则和验收场景：

- 团购成败由有效参团人数和截止时间共同决定；
- 订单、库存和参团人数在支付、取消、关团退款等路径中保持一致；
- 用户、团长和管理员的角色权限与数据归属分别检查；
- AI 导购以需求订阅和团购匹配为业务场景，当前实现边界以规则解析为准。

以上属于工程实现与集成方面的课题特色，不宣称在拼团算法、大语言模型或供应链理论上形成原创突破。

## 八、项目范围与当前状态

### 本期范围

- 用户与团长注册登录、管理员登录和角色授权；
- 商品浏览与管理、开团、参团、模拟支付、订单管理；
- 成团、到期解散、超时关单、取货码核销和模拟退款；
- 评价、站内消息、管理员基础统计；
- 面向本地教学演示的单体部署。

### 不纳入本期

真实支付渠道、商家入驻、骑手配送、佣金结算、优惠券或秒杀、短信和 App 推送、原生 App 或小程序、评价审核，以及大语言模型解析服务。

### 当前实现口径

现有 OpenSpec 基线覆盖用户角色、商品、团购、库存、订单、核销、管理看板、评价、消息以及 AI 导购的需求订阅与评价洞察，共 11 个 capability。AI 导购变更已于 2026-10-17 完成端到端实测并归档，后端 52 个集成测试全绿、前端构建通过。界面设计和实际页面完成度存在差异，应以 [`实现清单`](implementation-inventory.md) 的状态标注为准。

## 九、可行性分析

- **技术条件**：项目已采用 Java 17、Spring Boot、MySQL 和 Vue 3 等成熟 Web 技术，代码按 Controller、Service、Mapper 等层次组织；具体版本与理由见 [`技术选型介绍`](technology-selection.md)。
- **业务范围**：课题围绕一个主要交易闭环展开，支付和物流等外部复杂环节以模拟或边界说明处理，便于在毕业设计周期内完成。
- **验证条件**：项目有 OpenSpec 需求规格、后端测试源码和验证报告，可用于追踪需求、实现位置及验证证据；报告未覆盖的项目仍需按当前计划补充验证。
